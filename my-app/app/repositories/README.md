外部APIへの接続処理を記載

```
タイムアウトを設ける
外部 API が応答しない場合に、BFF の処理や接続が長時間残らないようにします。fetch の signal にタイムアウトを設定し、タイムアウトと通常の通信エラーをログで区別できるようにします。

res.ok を確認する
fetch は HTTP 404 や 500 では例外を投げません。現在のコードはその場合も res.json() に進むため、ステータスを確認してから本文を読むようにします。必要なら 429 や 5xx は別扱いにし、上流 API の Retry-After も考慮します。

型アサーションだけに頼らない
as IJPPostsResponse は TypeScript 上の型を付けるだけで、実際のレスポンスがその形かは確認しません。外部データを信頼せず、必要な項目や型を実行時に検証してからアプリ内部で使うのが安全です。

失敗の情報を適切に残す
現状の catch は通信エラーや JSON の解析失敗を同じエラーに置き換え、元の原因を失います。利用者には内部情報を出さず、サーバーログには上流のステータス・処理時間・エラー種別などを安全に記録すると、障害調査がしやすくなります。console.log の代わりに、アプリ共通のロガーを使う方針は良いと思います。

URL を環境設定に移す
TODO にあるとおり、API の URL は環境変数などの設定に分けると、環境ごとの差し替えが容易です。起動時に未設定や不正な URL を検知できるようにし、ユーザー入力をそのまま接続先に使う設計は避けてください。API キーを使う場合はサーバー側だけで扱います。

リトライは条件と回数を限定する
一時的な通信障害や 429・5xx に限って、回数上限と待ち時間を設けて再試行するのが基本です。4xx 全般や不正な JSON を無条件に再試行すると、復旧を遅らせたり上流 API に負荷をかけたりします。まずタイムアウトや失敗状況を計測し、必要性を確認してから導入するのがよいです。

キャッシュの可否を決める
投稿データのように共有可能で更新頻度が低いデータなら、短時間のキャッシュで応答時間や上流 API の負荷を抑えられる場合があります。ユーザーごとの情報を含むデータでは、キャッシュキーや共有範囲を慎重に設計してください。
```
